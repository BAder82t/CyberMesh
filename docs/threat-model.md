# Threat model

Scope: CyberMesh v0.3.7 as implemented in this repository. The method is asset- and
adversary-driven and STRIDE-informed. For each threat this document gives the mitigation,
the test that exercises it, and the residual risk. "Test" names refer to files in this
repository.

## 1. Assets

1. **Integrity of published intelligence**: no benign site is blocked, and nothing is silently dropped.
2. **Availability of protection**: consumers keep working through outages.
3. **Participant safety**: worker hosts are never made to execute foreign code, fetch hostile content or leak data.
4. **User privacy**: browsing activity never leaves the browser.
5. **Accountability**: misbehaviour is attributable using signed evidence.

## 2. Adversaries

| ID | Adversary | Capabilities assumed |
|---|---|---|
| A1 | External network attacker | Can observe, inject, drop, replay and delay traffic, and connect to public endpoints |
| A2 | Malicious or compromised worker | Holds one enrolled worker key, can sign anything, and can run modified code |
| A3 | Colluding operators | Control all workers of up to *t* organisations, including *t* ≥ the operator threshold |
| A4 | Sybil attacker | Can create many keys or peer ids, or one organisation can enrol many workers |
| A5 | Compromised release-signing key | Holds one release key (or several keys of one organisation) |
| A6 | Feed poisoner | Can get entries into a public reference feed |
| A7 | Malicious anchor or calendar | Controls a timestamp calendar or a chain node |
| A8 | Supply-chain attacker | Controls a dependency or a build input |
| A9 | Curious infrastructure operator | Runs a release host, calendar or relay and wants to learn about users or participants |

Out of scope: an adversary holding a threshold of governance keys, an adversary holding a threshold of release-signing keys from distinct organisations, compromise of the end user's browser or OS, and kernel-level compromise of a worker host. The last one affects that host's own results, which verification then catches.

## 3. Threats and mitigations

| # | Threat | Mitigation | Evidence (tests) | Residual risk |
|---|---|---|---|---|
| T1 | **Malicious worker node** submits false assessments (A2) | Verifier recomputes every task with pinned evidence; any differing signed result is a provable `IncorrectResult` fault → quarantine; classification uses the verifier's own assessment | `verifier/tests/adversarial.rs::single_malicious_worker_is_caught_by_recomputation`; `tests/adversarial::forged_verdicts_are_caught_and_quarantined` (real network) | A verifier without matching evidence cannot recompute (then: no `block`, disputes unresolved) |
| T2 | **Sybil**: one org enrols many workers or peer ids to fake diversity (A4) | Membership is governance-signed; diversity counted per *operator*; worker's operator bound by manifest; peer allowlist from manifest | `one_operator_with_many_workers_is_not_diverse`; `results_bind_worker_identity_and_operator`; `unenrolled_peer_cannot_connect_or_inject` | Governance must vet organisations; collusion between distinct real organisations is T7 |
| T3 | **Compromised organisation computer** (A2 on a member host) | Same as T1; key revocation in the manifest; workers run as unprivileged user with OS sandboxing (systemd unit); no inbound code | `revoked_worker_results_are_rejected`; `revoked_issuer_is_rejected`; `revoked_peer_is_disconnected_and_ignored` | Key theft until the revoking manifest reaches nodes (reloaded every 60 s) |
| T4 | **Task forgery** (A1, A2) | Tasks must be signed by an enrolled issuer; issuer field must equal signer; DSSE payload-type separation; canonical encoding | `forged_tasks_are_rejected`; `oversized_and_malformed_inputs_are_rejected`; fuzz target `task` | Compromised issuer key can issue bogus *tasks* (not results/releases): bounded by allowlisted kinds and limits |
| T5 | **Malicious updates**: tampered binaries, manifests or releases (A8, A1) | Manifests are k-of-n governance-signed with sequence numbers; releases are k-of-n operator-signed with anti-rollback; reproducible deterministic release bytes; `--locked` builds, pinned toolchain, `cargo-deny`, SBOM, actions pinned by SHA | `manifest_requires_governance_threshold_and_rejects_rollback`; `anti_rollback_and_equivocation`; CI | Binary release signing and reproducible-build attestation are not yet published (roadmap) |
| T6 | **Threat-feed poisoning** (A6) | Popular and hosting-platform evidence prevents blocking popular services; feed snapshots are pinned by digest and bound to their kind; upheld appeals suppress re-listing from lexical evidence; feed listing is necessary but not sufficient for `block` | `popular_domain_overrides_feed_listing`; `colluders_cannot_turn_a_feed_false_positive_on_a_popular_domain_into_a_block`; `relabelling_a_source_changes_its_pin` | A poisoned entry for a non-popular legitimate site *will* be blocked if the verifier trusts that feed: feed choice is a governance decision; appeals are the remedy |
| T7 | **Reputation manipulation / collusion** (A3) | Reputation is never evidence; one fault quarantines; colluders need the verifier's own feed corroboration for `block`; recomputation catches identical lies | `colluding_operators_cannot_cause_block`; `reputation_apply_is_idempotent` | Colluders that *agree with the truth* gain reputation (harmless); a colluding *verifier* is T15 |
| T8 | **False-positive attacks**: getting a competitor blocked (A3, A6) | Block requires feed + verifier corroboration + non-popular; lexical-only → advisory `warn`; public corrections; appeals; consumer dismissal of warnings | `block_requires_independent_corroboration`; `appeal_covers_subdomains_and_only_fresh_block_relists` | An attacker who can get a site into the trusted feed can cause a block until appeal |
| T9 | **Denial of service** (A1, A2) | Envelope size limits; per-author token buckets; bounded queues/replay cache (fail closed); connection limits; bounded rejection logs; parser budgets (OTS nodes/bytes, recursion) | `per_peer_rate_limit_drops_floods`; `rejection_log_is_bounded_under_flooding`; `breadth_amplification_is_bounded`; fuzzing | Enrolled peers can still consume their rate allowance with valid messages; invalid ones get them graylisted (T29) |
| T10 | **Replay** of tasks, results, releases (A1, A2) | Replay cache keyed by payload digest until expiry; results bound to task digest + attempt; gossip ids `H(author‖data)`; release anti-rollback state | `replay_cache_rejects_redelivered_task`; `replayed_late_unassigned_and_mismatched_results_are_rejected`; `tests/adversarial::replayed_results_are_rejected` | A consumer that loses its state can be rolled back to any still-unexpired release (max 30 days) |
| T11 | **Key compromise**: worker, issuer or verifier key (A2) | Revocation list in manifest; role separation; key files 0600, no symlinks, fstat on open handle; keys zeroised in memory | `key_file_roundtrip_and_permissions` | No HSM support yet; revocation latency = manifest distribution |
| T12 | **Compromised release-signing key** (A5) | k-of-n signatures from *distinct operators*; revoked keys excluded from trust root; equivocation detected | `threshold_counts_distinct_operators`; `revoked_signing_key_no_longer_counts`; extension unit tests | Consumers must update their bundled trust root to drop a revoked key (extension update) |
| T13 | **Supply-chain compromise** (A8) | Minimal dependencies; `cargo-deny` (advisories, licences, sources); SBOM per CI run; secret scanning; Actions pinned to SHAs; extension has zero runtime dependencies | CI workflow | Transitive crates (libp2p) are large. One third-party crate, `if-watch`, is vendored with a five-line change (`vendor/if-watch/VENDORED.md`), so its source is in the repository and `paste` is out of the build |
| T14 | **Metadata leakage** (A9) | Extension downloads the whole list (no per-URL lookups); release host learns only "a client fetched the list"; anchors receive one 32-byte hash, OTS adds a random nonce; worker results contain no org-internal data | `privacy.md`; extension e2e asserts only the release URL is requested | Release host sees client IPs and fetch times; peers see each other's IPs and participation |
| T15 | **Malicious verifier or issuer** (A2 on coordinator) | Independent verifiers at other organisations recompute every task with their own engine and key. Releases need matching records from `min_verifiers` distinct verifier operators (manifest). Records name their verifier inside the signed payload, and release builders check the name against the signer and the manifest. Release signers *independently rebuild* releases. | `one_verifier_can_neither_list_nor_escalate_alone`, `quorum_counts_operators_not_keys`, `records_must_name_their_actual_signer_and_its_operator`, `an_independent_verifier_completes_the_release_quorum` (real network) | `min_verifiers` colluding verifier organisations can still publish. Fewer than `min_verifiers` live verifiers halt new publication (availability). An issuer can withhold or skew *which* domains are tasked, and for CT *which tiles*: `cybermesh ct report` lists the holes between verified tile ranges (`ct-monitoring.md` §8), though not tiles after the last one. With `min_verifiers = 1` (the default), the single verifier is trusted as in v0.1 |
| T16 | **Malicious blockchain attestations** (A7) | Anchors only receive a commitment; OTS proofs evaluated offline with bounded parser; upgrade only contacts configured calendars; Bitcoin attestations must be checked against the user's own node; anchors are not trusted for protection | `breadth_amplification_is_bounded`; `stamp_against_mock_calendar_and_verify_offline`; `injected_failures` | A calendar can lie about pending status (harmless: no protection decision depends on it) |
| T17 | **Network partitions** (A1) | Workers redial bootstrap peers; bounded outbox until deadline; coordinator reassigns tasks to other live operators; consumers use cached, unexpired releases | `reconnects_after_peer_restart`; `disconnected_worker_is_replaced_by_reassignment` | Long partitions delay new intelligence; releases expire after their TTL (fail-safe, not fail-open) |
| T18 | **Arbitrary code execution / scanning via workers** | No task carries code, scripts, URLs or commands; one allowlisted kind; engine never makes network requests; adversary simulation is a non-default compile-time feature | Code review; `assess` has no I/O | A worker binary built with `adversary-sim` misbehaves only against its own reputation |
| T19 | **Parser exploitation** (A1) | Strict canonical JSON, `deny_unknown_fields`, size limits, no `unsafe` in project code, property tests and fuzz targets for envelopes, tasks, releases, OTS proofs, domains | proptests in every crate; `fuzz/` | Dependencies (serde_json, libp2p) are trusted |
| T21 | **SSRF or unwanted egress through CT tasks** | Tasks carry no URLs. Only `checkpoint` and `tile/...` paths (for a classic log, `ct/v1/get-sth`, `get-entries`, `get-proof-by-hash` and `get-sth-consistency` with integer and base64 arguments) under pinned `ct-logs` monitoring prefixes are fetched (HTTPS to a DNS host name, or loopback HTTP). No credentials, percent-encoding or IP literals in prefixes. No redirects; HTTP 200 only. Size caps after decompression. Opt-in per operator. | `ct_log_url_policy`; worker code review | DNS rebinding of a pinned HTTPS host is out of scope (TLS authenticates the host). |
| T22 | **Hostile certificates in CT logs** (anyone can log certificates) | Bounded TileLeaf parser with required `leaf_index`, `x509-parser` pinned and part of the engine version, at most 1000 names per certificate and 8,192 per tile, 4 matches per certificate and 16 per tile kept by risk, 16 MiB tile cap, edit distance only for near-equal lengths, fuzzing | `ct_tile` fuzz target (1.2 M + 2.3 M runs); `arbitrary_bytes_never_panic`; `caps_keep_the_highest_risk_matches_and_commit_every_name` | Dependency (`x509-parser`) is trusted |
| T23 | **CT workers lie**: hide, alter or fabricate matches, or skip downloads | Tile roots checked against the log's roots, proven against its checkpoint signed with the pinned key (a fault only once the verifier's own scan matches the proven root); a digest of every extracted name; secret spot checks, one biased to tiles that report matches; full rescan on disagreement; confirm-before-publish for every published finding | `ct_adversarial.rs` (10 tests); `tests/integration/ct_e2e.rs` | Two colluders omitting the *same* match and reporting the tile empty escape with probability `1 − 1/tile_count` per task (omission only) |
| T24 | **False positives from CT** (brand owners' own infrastructure) | Investigation-only by default. Publishing is opt-in, needs a typosquat or homograph signal and a minimum score, and is capped at `warn`. | `by_default_ct_findings_are_for_investigation_only` | Brand tables need owner-maintained infrastructure lists |
| T26 | **Forged CT log data** from a CDN, mirror or network attacker (substituted checkpoint or hash tiles) | Checkpoints are verified against each log's pinned ECDSA P-256 key and origin (C2SP signed note, RFC 6962 `TreeHeadSignature`). Tile roots are proven against the signed root. Hash tiles that contradict it mark the tile log-inconsistent: the task is disputed and nobody is faulted. | `verifies_a_real_static_ct_log_checkpoint`, `rejects_unsigned_malformed_and_extended_notes`, `proves_tile_roots_for_trees_with_partial_tiles_at_every_level`, `a_tampered_hash_tile_is_detected`, `checkpoints_and_tiles_that_the_log_did_not_sign_are_refused`, `hash_tiles_contradicting_the_signed_checkpoint_dispute_the_task`; `ct_checkpoint` fuzz target | In follow mode a log that rewrites its history is detected: each checkpoint must provably extend the previous one (`consistency_between_checkpoints_is_proven_from_tiles`). A split view, where different viewers are shown different but self-consistent trees, is T28. Pinned keys must be updated when logs rotate. |
| T25 | **Malicious or flooded verification records** on the `records` topic (A1/A2) | **Authentication.** Records are checked on receipt with the same function release builders use: enrolled verifier signature, network id, named verifier equals signer and its operator. Future-dated, older than 30 days and own records are refused.<br>**Storage.** Records are stored re-encoded with only the verifier's own signature, under digest-derived names. The store is bounded in records and bytes, overall and per operator, with at most 2 records per operator and task. It is pruned by age and re-checked on every manifest update.<br>**Forwarding.** Only valid new records are forwarded. Peers are penalised only for provable forgery.<br>**Building.** Release builders re-verify every file against the build-time manifest and skip, and name, those that fail. | `stores_only_valid_records_of_other_verifiers`, `rewrapped_records_are_stored_normalized_and_quotas_hold`, `revoked_verifiers_records_are_removed_and_old_ones_pruned`, `records_must_name_their_actual_signer_and_its_operator`, `an_independent_verifier_completes_the_release_quorum` (real libp2p) | An enrolled verifier can use its own operator's quota. Partitions delay records, and with them publication. Organisations whose nodes received different record sets build different payloads and cannot co-sign until they reconcile. |
| T20 | **Evidence tampering on a worker host** | Evidence files verified against bundle digests; pins bound to kind; symlinks/special files refused; size caps | `verifies_digests_and_parses_lists`; `refuses_symlinked_sources` | Local root can change both files and code (caught by recomputation) |
| T28 | **CT log split view**: a log (or whoever holds its key) shows different organisations different trees, each consistent on its own, for example to hide a certificate from some monitors | **Witnessing.** Verifiers poll the log's checkpoint, accept it only if signed by the pinned key, fresh and consistent with their previous one, cosign it (C2SP `cosignature/v1`) and publish it on the `checkpoints` topic.<br>**Comparison.** Each compares peers' checkpoints with its own view, using hash tiles authenticated against its own signed checkpoint. Two checkpoints the log signed that cannot belong to one append-only log are written as a proof anyone can check offline with the log's key.<br>**Consequence.** The log is no longer relied on: following halts and its CT tasks are settled without log access.<br>**Abuse.** Observations must be signed and cosigned by an enrolled verifier naming itself and carry a checkpoint the log signed, so no peer can fabricate a split view. At most one pending observation per peer and log, compared at most once a minute. | `a_forked_view_is_proven_with_a_checkable_consistency_proof`, `a_split_view_proof_is_checkable_offline_and_cannot_be_forged`, `cosignatures_follow_c2sp_and_keep_the_log_signature_valid`, `two_views_of_one_log_are_caught_and_proven_on_both_sides`, `observations_are_refused_unless_signed_cosigned_and_current`, `unreadable_tiles_prove_nothing_and_are_given_up`, `a_log_showing_organisations_different_trees_is_proven_and_not_followed` (real libp2p) | Only the views of witnessing CyberMesh verifiers are compared: a log showing all of them the same fork is not caught without external witnesses. Detection takes up to a poll and a publish interval (1 and 5 minutes by default). An enrolled verifier can make peers download a few hash tiles per minute. |
| T29 | **An enrolled peer floods invalid messages** (forged or misattributed envelopes, proven faults) (A1/A2) | **Author penalties.** A message the application `Reject`s counts against its author (authenticated by its gossipsub signature), never against relays. One invalid message is tolerated. About two within ten minutes take the author out of the mesh and stop gossip with it. About three graylist it: everything it authors is dropped before validation, whichever peer relays it. The count halves every 10 minutes and survives reconnection.<br>**No honest peer is charged.** `Reject` is reserved for what no software version, manifest timing or clock can explain (`ProtocolError::proves_misbehaviour`, `Rejection::misbehaviour`): a broken signature by an enrolled key, a claimed identity that is not the signer, another network, unassigned or faulted workers, proven faults. Clock skew, a lagging manifest (unknown signers, assignees, operators), a newer release's fields or limits, late or superseded results, unusable cosignatures and quotas are `Ignore`d.<br>**Nothing can be earned.** No rewards for time in the mesh or deliveries, so good behaviour cannot be banked against attacks. | `a_peer_sending_invalid_messages_is_graylisted`, `ignored_messages_never_cost_a_peer_anything`, `invalid_messages_count_against_their_author_not_the_relay` (real libp2p); `scoring_costs_only_invalid_messages_and_forgets_them_slowly`; `only_what_an_honest_node_cannot_send_proves_misbehaviour`; `only_what_no_version_or_manifest_explains_proves_misbehaviour`; `rejections_say_whether_they_prove_misbehaviour` | Malformed messages that might be a newer format are not charged, so an attacker can send them up to its rate allowance. Penalties are local to each node. A graylisted author is heard again once its count decays, after a few minutes; while graylisted it cannot relay for others either. A worker that signs two results asserting different things for one task is treated as equivocating and also counts towards graylisting; the same answer signed again (for example after a restart) is only a duplicate. |
| T30 | **A lying worker that only an independent verifier catches**, or **a verifier falsely accusing a worker** (A3; a compromised verifier) | **Proofs with evidence.** An independent verifier whose own checks prove a fault (its CT spot checks use its own secret seed) publishes a fault proof. The proof carries the issuer-signed task and the worker's signed results.<br>**Checked before acting.** The coordinator quarantines the worker only after confirming the fault itself: from the signatures for equivocation and mismatched results, by its own recomputation for domain tasks, and by re-scanning log-proven tiles for CT tasks. Refuted or undecidable claims change nothing, and neither do CT claims about a log proven to show a split view.<br>**Bounded.** Each check has a time budget. Reporters take turns with bounded queues. A proof with another kind over the same results, or one that could not be decided, cannot stop the real fault from being checked. | `equivocation_and_mismatched_results_are_confirmed_from_signatures_alone`, `an_incorrect_result_is_confirmed_only_by_the_checkers_own_recomputation`, `an_incorrect_ct_result_is_confirmed_by_rescanning_the_log`, `evidence_must_be_the_accused_workers_own_results_for_this_task`, `proofs_are_signed_by_the_verifier_that_reports_them`, `intake_dedupes_queues_per_reporter_and_takes_turns`, `an_undecided_check_does_not_hide_the_fault_for_good`, `a_proof_about_a_log_proven_split_is_not_confirmed`, `the_same_answer_signed_again_is_a_duplicate_not_equivocation`, `a_late_result_is_equivocation_only_if_it_asserts_something_else`, `settled_evidence_is_bounded_and_expires`, `a_late_contradicting_result_is_proven_and_published_for_the_coordinator`; `the_coordinator_quarantines_workers_another_verifier_proves_lied` (real libp2p: colluding workers the coordinator accepts, caught by the verifier, quarantined by the coordinator) | A fault the coordinator cannot re-check (another engine or evidence version, no log access) is not acted on. Quarantine affects future assignments, not records already signed. A false accusation is refuted but not penalised. A verifier proves late equivocation only for tasks whose evidence it still holds (32 MiB, oldest first) (older tasks are still caught by the coordinator if it saw both results). |
| T27 | **Spoofed DNS for a peer's host name** (`/dns4/...` bootstrap address; network attacker) | Nodes dial only addresses in their own configuration, never addresses supplied by peers. Every bootstrap address names the peer id, which the Noise handshake authenticates, so a connection to any other key fails | `peers_connect_through_a_dns_address`; `a_dns_address_cannot_substitute_another_peer` (fails if the address names the impostor's id) | Spoofing can block or delay a connection to that peer (a denial of service), as an IP-level attacker can already |

## 4. Findings from internal reviews

Two independent internal reviews (security and Rust correctness) examined the core crates. Every
confirmed or plausible finding of HIGH or MEDIUM severity was fixed with a regression test. See
[security-review.md](security-review.md). This is not an external audit.

## 5. Explicit non-goals

- CyberMesh is not an anonymity system. Participants are known organisations.
- It does not protect against all malicious websites; it covers only hosts in the current release.
- It does not replace endpoint security, mail filtering or browser Safe Browsing.
